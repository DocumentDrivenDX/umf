# Exact executed-read identity: documented metadata research

Source/docs-only research on2026-10-17. No native/auth/queryhistory API or systemtable has been called. The pending read-only owned-history plan is not permission to execute. No tableUUID oracle is inferred from SQL/source hashes or a name.

[Query History REST reference](https://docs.databricks.com/api/query-history/v1/query-history) documents GET /api/2.0/sql/history/queries with exact statement_ids and warehouse_ids filters. Its schema exposes executing identity, cache provenance, finality and whether plans exist, but no resolved native tableUUID or profilebody. Those fields can establish historical framing and expose missing/cache cases; they do not alone establish resolved-table identity.

[Official Python SDK sql.py](https://raw.githubusercontent.com/databricks/databricks-sdk-py/main/databricks/sdk/service/sql.py) currently implements QueryHistoryAPI.list using that route; QueryInfo mirrors the identity/cache/planavailability fields. There is no query_profile method in the inspected file. This is live official source inspected on this date, not a claim about a pinned deployed SDK. No guessed private profile endpoint is used.

[Azure query profile documentation](https://learn.microsoft.com/en-us/azure/databricks/sql/user/queries/query-profile) describes UI download of native profile JSON, requiring the queryowner or CAN MONITOR. It explicitly excludes cache-served queries from profiles. It does not document a REST profiledownload API or guarantee immutable tableUUID fields. A UI-exported original JSON may be a later discovery artifact if the exact ownedStatementId can be opened; native metadata availability, actual IDs, cache completeness and retention still need proof. No suggestion to change LIMIT/reexecute is adopted, because that would change the exact observed statement.

[Azure lineage systemtable reference](https://learn.microsoft.com/en-us/azure/databricks/admin/system-tables/lineage) ties records to statement_id but lists names/paths, not source_table_id. It warns capture is partial and describes one-year systemtable retention. Therefore lineage names and paths cannot be substituted for an immutable UUID or a completeness certificate. Systemtable reads would also need compute/systemschema permissions, so they are excluded from the proposed no-compute metadata discovery.

`owned-history-read-plan.json` proposes just TWO documented GETs, one per original retained native009/015 StatementId on the dedicated warehouse, exact sourcefile/SQLhash and warehousefilter retained. max_results1, no nextpage, <=20seconds/call and45seconds total, no retry/redirect/compute/SQL/newresource. Every returned record must match exact query_id+warehouse. No spark_ui_url/lookup_key/private route is followed. Missing/ambiguous/foreign framing refuses. These original statements are mutation fixtures, so any metadata observation is discovery only and cannot itself qualify current search reads or Delta mutation fencing. A useful result may simply confirm profileavailable/cacheidentity while the actual tableUUID requirement remains unresolved.

If future native profile data supplies a complete actual resolvedtable UUID set for the exact SELECT StatementId, the runtime could buffer its bounded <=1hydration row, validate that native evidence, and withhold output on mismatch/missing evidence. That is a bounded read-only postdispatch validation candidate, distinct from a predispatchwrite fence. It requires original-owner adoption and native concurrentDDL/cache tests before acceptance; neither this source nor the current runtime implements an invented authority signal.
