# Delta atomic receipt source audit

Disposition on 2026-10-17: **no supported complete exact native commit-result receipt mechanism identified** for the inspected Databricks SQL interfaces. This is a bounded source/documentation finding, not a claim that no future or private native interface can exist. CONTRACT-073 execution qualification and temporal qualification remain **HELD**. No cloud call, compute/resource creation, native transaction, compiler implementation edit or public compiler publication was performed for this audit. R22 source `5605d358650468d651f69ff29c40e986a0359a5b` and the separate private Delta prototype are unchanged.

## Required meaning and retained native observations

[CONTRACT-073](../../../../02-design/contracts/CONTRACT-073-native-sql-action-profile.md#native-receipts-and-original-transaction-scope) requires a receipt containing exact native table UUIDs and ordered per-table committed versions, bound to this atomic commit and the admitted store incarnation. A later history head is insufficient. Attribution metadata is separate from that receipt; uncertain committing requests remain indeterminate under the contract.

The previously retained native exploration observed a successful two-table `BEGIN ATOMIC` statement whose history records share a transaction identifier and its exact statement identifier, at objects version 2 and receipts version 1. Later heads were 3 and 2, so those particular records are historical attribution observations rather than a latest-head guess. Statement 015 also linked to two history records, but it executed `UPDATE value=value` and inserted a receipt. It does not prove a compiler-admitted no-op that skips the business write. The private prototype conditionally skips an unchanged UPDATE; a table with no native commit cannot be assigned an invented new version.

The original native cohort's `verification.json` remains `cleanup-failed` with a timeout. Its separate recovery receipt records the warehouse stopped. Neither that recovery nor this audit retroactively changes the original cohort disposition or supplies missing exact receipt semantics. Existing [managed runtime evidence](../managed-runtime-20261017/README.md) remains separately scoped.

## Interface findings

| Inspected original interface | Supported information | Exact-receipt limitation |
| --- | --- | --- |
| [Statement Execution response](https://docs.databricks.com/api/statement-execution/v1/execute-statement) | Statement identifier, status, manifest and result data | No documented native table UUID/version vector field. The retained successful atomic responses contain an empty result manifest. A statement identifier is execution custody, not itself a version vector. |
| Installed Databricks SQL Connector for Python 4.6.0 | `Connection.commit()` executes native COMMIT and returns `None` | Its implementation does not fetch the COMMIT cursor's result. Inspected typed Thrift/Statement API response surfaces expose no declared native commit vector; generic diagnostics or arbitrary result rows are not a documented receipt contract. Exact installed source hashes are in `local-observations.json`. |
| [COMMIT syntax](https://docs.databricks.com/aws/en/sql/language-manual/sql-ref-syntax-txn-commit) | Commits the active interactive transaction | No documented RETURNING/table-version-vector result. Interactive support does not satisfy the separately governed BEGIN ATOMIC profile by itself. |
| [GET DIAGNOSTICS](https://docs.databricks.com/aws/en/sql/language-manual/control-flow/get-diagnostics-stmt) | Transaction-active state and most recent DML affected-row count | Neither item supplies native commit identity or a per-table committed version. A row count does not distinguish a committed no-op receipt from a later table snapshot. |
| [Session last commit version](https://docs.databricks.com/aws/en/tables/history#find-the-last-commit-version) | One last committed version for the SparkSession, across tables and threads | Not a UUID-keyed vector. Session sharing introduces additional races; exclusive use alone does not turn one scalar into all affected-table commit results. |
| [Table history schema](https://docs.databricks.com/aws/en/tables/history-schema) | Per-table version, operation, read version, metrics and optional user metadata | The documented fourteen-column schema does not specify the observed `queryHistoryStatementId` or `operationMetrics.txnId` linkage. Some fields are unavailable through JDBC/ODBC/REST. Retention and omitted/no-op records prevent treating absence as proof of noncommit. |
| [Query history system table](https://docs.databricks.com/aws/en/admin/system-tables/query-history) | Statement/session identifiers and execution metrics | Typically delayed up to roughly an hour and privileged; it documents no all-table commit-version vector. Timing or written-row metrics cannot establish receipt completeness. |
| [Custom commit metadata](https://docs.databricks.com/aws/en/tables/operations/custom-metadata) | Writer-authored metadata readable in history | Application-authored correlation is not native commit-result attribution. The documentation does not promise atomic-block coverage for every table/no-op; serverless also restricts the session-configuration route. No automatic ledger/marker substitution is proposed. |

The current official [Delta transaction protocol](https://github.com/delta-io/delta/blob/master/PROTOCOL.md#writer-requirements-for-catalog-managed-tables) does require a unique `commitInfo.txnId` for catalog-managed commits. This strengthens the underlying log identity premise beyond a wholly undocumented transaction identifier. It still does not specify Databricks SQL exposure through `operationMetrics.txnId`, mapping from a returned statement identifier, a complete multi-table commit response, or a representation for a business table whose no-op write was skipped. The inspected protocol URL is a moving upstream branch, not a pinned installed runtime guarantee.

The [Databricks transaction overview](https://docs.databricks.com/aws/en/transactions/#how-transactions-appear-in-the-delta-log) documents one log entry per successful transaction on a table and nested operation metadata. That supports examining native commit records; it does not make the observed history linkage a supported complete receipt API. System-table queries and time travel also have transaction restrictions. Reading a later history record is not silently promoted to the native commit result required by the current contract.

## Next executable gate

There is no qualifying end-to-end implementation to enable from this audit. The existing shipped predispatch refusal must remain. The next useful executable step is a **separately authorized native capability discovery**, only if a documented native interface or reviewed original-owner profile supplies the missing attribution guarantee. Repeating atomic ACK/history-head tests alone would not close the prerequisite.

That bounded gate must retain the complete raw native commit response and the original statement/transaction identity, independently pin every original table UUID, and exercise: (1) two changed tables; (2) one changed plus one skipped no-op table; (3) all business effects skipped; (4) a later concurrent writer on each table before receipt consumption; (5) signaled rollback; (6) response loss after dispatch without automatic retry; and (7) dropped/recreated table identity and missing/expired metadata. The oracle must prove an exact complete per-table vector for the original attempt, including an explicitly supported no-op convention, without borrowing another writer's version or inventing a missing commit. Missing attribution must remain indeterminate or unqualified as the governing phase requires.

Before writing or running that gate, obtain the native interface's source/version contract for all-table completeness, stable UUID association, no-op attribution, retention, and loss behavior. The observed statement-ID/history linkage can be tested as a diagnostic candidate but cannot be labeled supported or contract-complete merely because examples correlate. Any proposal to accept history-derived receipts or change the no-op convention requires explicit governing review; this audit grants no semantic waiver.
