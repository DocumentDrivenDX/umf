# Contract: Storage layout

**Contract ID**: CONTRACT-001
**Type**: schema
**Version**: layout 0.2 (draft)
**Status**: draft
**Related**: ADR-002 (storage strategy), ADR-001 (language and portable core), SPIKE-002, SPIKE-003, the storage layout review, CONTRACT-002 (journal), CONTRACT-003 (catalog), CONTRACT-004 (mutation and conformance)

## Purpose

Defines the fixed set of PostgreSQL tables truss stores UMF-described property-graph data in, so that any implementation, in any language, reads and writes the same tables. The executable form is [`storage-layout.sql`](storage-layout.sql), checked by [`storage-layout.check.sql`](storage-layout.check.sql). A conforming implementation is interchangeable with another over the same database.

The PRD and feature specifications now frame Truss. This contract implements ADR-002 and remains draft pending requirements/design reconciliation and qualification.

## Scope and Boundaries

- In scope: tables, columns, constraints, sequences, indexes, identity, key identity, value encoding, deletion, locking, enforcement layering, host roles and extension rules, supported PostgreSQL versions.
- Out of scope: how a UMF document becomes catalog rows (CONTRACT-003), the journal's content and ordering (CONTRACT-002), the mutation operations and the conformance corpus (CONTRACT-004), the query language, generated per-type tables.
- Owning project: truss. Consumers: truss's own engine, and any other implementation (for example a Python implementation embedded in an application).
- Every element carries a source: **ADR-002** (with its decision number), **SPIKE-002** or **SPIKE-003** (a measurement), or **Proposed** (set by this contract and not yet in an ADR). Points that ADR-002 marks provisional are marked so here.

## Normative Surface

### Proposed catalog owner and definition source homes

#### Proposed fixed row-home value model

ADR-002 D4 requires fixed value-row tables with typed scalar columns; baseline layout 0.2 has only the json/row catalog tag and no value-row realization. Propose an additive, separately versioned row-home layout with three fixed logical stores: property presence/root state, value-tree nodes, and typed scalar payload stores selected by the complete scalar profile. No per-type/property tables, partitions or columns are created during catalog acceptance. This is a candidate model, not adopted DDL or support for existing row tags.

For an edge, relationship identity and property-owner type identity are separate domains. The property FK proves the property belongs to its catalog type; the edge FK proves the graph edge belongs to its relationship. Neither proves their association. The protected producer/finalizer must resolve the original admitted edgeAssociationDefinition and verify that correspondence under the same catalog/authority cut. Numeric equality is insufficient and numeric inequality is not a rejection. Until that native association guard is qualified, edge row-home writes remain unavailable.

Presence/root state is owned by the full admitted object-or-edge typed identity and property ID, with immutable original value/definition/profile correspondence and actual owner version/revision semantics. No state row means absent only after complete authorized same-snapshot observation proves absence. A present state row binds exactly one root node; a null node and an empty sequence/map/record node remain distinct present values. Container emptiness cannot be inferred from absence of payload rows. A present scalar requires its matching typed payload and exact lexical/source carrier where promised. Numeric typed comparison values never replace original numeric tokens; timestamp instants never replace authored timestamp spelling.

Each node belongs to exactly one property state and has a full parent/slot identity: root, ordered sequence ordinal, literal map key or qualified authored record-field identity. Preserve one parent, no orphan nodes, no value-instance cycles, unique child slots and contiguous sequence order; authored type recursion remains permissible through its independently admitted finite value graph. Containers bind declared node kind and complete child inventory. A structured value retains its original record definition and member correspondence. Unknown content requires its exact retained source/opaque carrier and admission profile; unsupported native representation refuses the write rather than dropping nodes or storing guessed typed values. No independently mutable props shadow is maintained for a row home.

Native scalar payloads use selected typed columns and one-to-one node/family ownership. Exact type/domain/codec/null/comparison and source-byte custody are explicit inventory/profile outputs; absence of a selected family store is unsupported, not a string fallback. Read reconstruction independently compares complete state/node/payload ownership and definition, preserves empty/null/absence and exact original tokens, then publishes only the whole admitted value. Weft consumes the exact selected row join/location/codec binding and independently assessed comparator; an opaque row home or equal numeric IDs cannot authorize joins.

Mutations, import, catalog transforms, journal/history and home migration update full canonical state/tree/payload/key derivation and required provenance in the governing transaction/group protocol. Lock/admit the original graph owner and catalog/authority context before replacement; no partial tree, presence-only success or independent payload commit. Owner version and historical images change under existing record semantics. Row storage avoids whole props-map rewrites but does not assert independent-writer throughput or bypass owner locking; actual contention and alternate qualified concurrency procedures require measurement/design review. Deletion/replacement retains required original history/source/recovery evidence. Home switches require complete source-to-target value parity and atomic binding publication, never simultaneous ambiguous dual homes.

Concrete table/column/constraint/index/guard/grant inventory, typed family stores, node allocation/nonreuse, finite collection limits, complete writer/read/migration procedures and native qualification remain required before adoption. The candidate closes the conceptual presence/tree ownership model without claiming row-home generation is ready or narrowing the full scalar/collection objective.

##### Record candidate identity and source admission

RH02 record candidate construction uses CONTRACT-010's original record-field correspondence in the write direction. Resolve submitted full field identities against the complete original authored definition, reject duplicate identities before building candidate slots, and admit every required/optional/null/child value and separately retained content. Select the original full identity-byte encoder before native allocation; a display name, current same-named definition or equivalent reserialized JSON is not that selection. Missing optional fields have no child, present null fields have an admitted null child with no scalar payload, and empty records retain their actual container/root.

##### Row-home finalization procedure proposal

RH04/RH06 use the proposed `truss-row-finalization/0.1.0` procedure below. A finalization invocation is bound to the actual writer transaction, protected owner, original catalog/home generation and complete replacement candidate. It is not a caller-supplied boolean or reusable receipt. Native guard routines and their registered inventory remain to be implemented and qualified; this procedure specifies their required behavior rather than claiming the CHECK/FK fragment already supplies it.

The [row finalization resource proposal](bindings/truss-row-finalization-resource-v0.1.proposal.json) supplies explicit candidate ceilings: 1,024 touched property states, 65,536 nodes per value, 262,144 total node and payload occurrences each, depth 128, 4 MiB source per value, 32 MiB total source/decoded artifacts, 1 MiB per full slot identity, 128 MiB simultaneous owned memory, 512 MiB cumulative allocation, 64 million charged work units and a 30-second stage deadline. These are admission ceilings, not guaranteed simultaneous capacity or throughput. The enclosing operation/group/transaction budgets remain stricter where applicable; they accumulate across internal passes and cannot reset per property. Selected native transport/codec weights and statement/lock caps remain adoption outputs.

Resource accounting includes raw observations, repeated source/definition decode, exact-ID indexes, collision comparisons, traversal stacks, candidate/old/new reconstructed values and diagnostics under the enclosing operation profile. Reserve before collection/lookup/result allocation, charge repeated work and simultaneous buffers, and stop without partial publication on any bound/cancel/deadline failure. SQL row limits must return a bounded overflow sentinel or equivalent complete collector proof rather than silently truncating inventory. Native collector and codec adapters need exact finite selected budgets; the existing operation limits cannot imply an unbounded finalizer allowance.

CONTRACT-005 now specifies the proposed row protected-privilege responsibility matrix, private integrity/public disclosure separation and explicit incompatibility with baseline direct-DML profiles. Exact native role/grant/routine/policy realization remains required.

The finalizer must be unavoidable for every admitted producer: mutation, import, catalog transform, home migration, group path and administrative repair. The selected native privilege profile must deny ordinary writers direct state/node/payload mutation and unqualified entry into guard routines; protected routines must capture actual acting authority and use qualified inventory-bound objects. Either a qualified deferred commit guard independently rejects unfinished touched states, or the adopted transaction protocol must prevent host commit of an unfinalized operation under a proven native enforcement profile. A library-only convention cannot be classified as database enforcement. Registry, touched-set custody, native routine/grant definitions and bypass schedules remain concrete implementation/adoption outputs. No finalizer receipt transfers authority to a later transaction or changed home generation.

##### Proposed native row-home dirty-generation guard

For the reference implementation, propose `truss-row-dirty-generation/0.1.0`: a protected fixed transaction-touch store plus unavoidable native write observation and deferred finalization checks. This is the selected candidate to realize the deferred-guard branch above, not an adopted PostgreSQL deployment or a new public receipt API. Ordinary host finalization is not sufficient authority for the seal.

Each touch entry binds original namespace/layout generation, actual native transaction identity, full graph owner kind/ID/discriminator, independent property-owner type/property ID, dirty generation and sealed generation. Native transaction identity is captured by the protected producer, never accepted from caller bytes. Sealed generation starts unset. Original candidate/prestate/history/group custody is retained through the governing operation; a generation number cannot replace those artifacts. Fixed native homes, keys, routine bodies, trigger inventory and privilege definitions remain implementation outputs.

The [touch-store SQL candidate](row-home-touch-v0.1.proposal.sql) authors a fixed twelve-column custody table keyed by actual xid8 transaction identity and full owner/property tuple. dirty_generation and nullable sealed_generation are positive signed bigint values with sealed generation no greater than dirty generation; equality at commit still needs the protected check. The captured pg_current_xact_id default is not permission for caller-supplied transaction IDs. Protected first-touch admission independently captures and compares actual transaction identity, original layout/home/association and operation custody. No graph/property FK is imposed because deleted/cascaded originals must survive for finalization. Same transaction/tuple with changed original layout or home generation refuses rather than overwriting provenance. Native type/default resolution, routine/trigger/grant bodies and retained-row cleanup remain unresolved.

Original operation bytes bind the complete bounded transaction-local sequence of contributing operation/group custody references; they cannot retain only the last write or silently discard an earlier group result. Repeated writes to the same tuple advance one dirty generation and preserve all governing effects. Later finalization independently checks the current composed value and complete earlier/later operation obligations before sealing. Exact custody encoding/archive lookup and native accumulated resource counters remain realization outputs.

The [operation-custody body grammar](truss-row-operation-custody-v0.1.proposal.schema.json) closes original_operation_bytes as an ordered contributing-operation manifest. Each operation retains its original definition/input/prestate/admitted-candidate artifacts, actual native group custody identity and complete effect-obligation definition. A missing prestate is represented by the admitted absent-state carrier, not an omitted entry or invented empty object. Manifest entry ordinal is the zero-based position in this touch-local contributing-operation array, contiguous from zero; it is not CONTRACT-007’s executor-issued native operation ordinal. Native ordinals remain exactly originally issued, including burned gaps, and resolve through each original operationIdentity/nativeGroupCustodyIdentity and their protected registry artifacts. Operation identities are unique under original native custody, and each actual contributing operation appears exactly once in original execution order. A touch first reached by native operation 7 has manifest position 0; later native operation 11 can occupy position 1 without changing either native identity. Missing noncontributing or rolled-back operations do not create manifest holes, reset the issuer or authorize rebuilding identities from surviving positions. Maximum 1,024 entries is a proposal ceiling additionally bounded by the RF and governing operation/group/transaction profiles. Repeated writes by one operation retain complete candidate/effect correspondence; new operations append, never replace earlier entries.

The registered custody encoding is the original strict JSON bytes for this closed body, retained and hashed under the admitted artifact/profile; duplicate keys, invalid scalar text, unknown members and invalid canonical decimal ordinals refuse before host object parsing. No normalization, caller-supplied transaction identity, future mutation-group digest or self-seal digest is inserted. Native group identity resolves through the original protected registry before sealing, where original effects readiness/parity is independently checked; final application completion remains a later native registry transition and the manifest cannot assert it. Stored layout/home/owner artifacts must correspond exactly to the enclosing touch row and current protected generation. A structurally valid substituted artifact, unknown group, missing/reordered/duplicate operation or changed original context refuses. Exact registered byte encoder, native registry/archive lookup and full source/effect collector realization remain required.

Group resolution before sealing means original transaction-local effects readiness: complete admitted inputs/candidates, actual canonical/key/history/report effects and independent group invariants under the native writer, excluding the seal that is about to be produced. RF01–RF06 then seals the independently validated row scope; application finalization records complete operation results and all required seals; deferred commit checking requires that final application status. Neither readiness nor application finalization is committed or externally acknowledged. Requiring a seal-dependent application-finalized status before producing that seal, or requiring a committed receipt before commit, would be circular. Native group custody resolves these phases explicitly, preserving host-adopted/outer-scope pending results. Commit-unknown or dead/foreign custody cannot be reclassified from a still-visible application-finalized row. Request-free mutations retain their original operation/group evidence without inventing ADR-005 replay receipts.

Touch dirty_generation and operation effect_generation have different scopes and must not be numerically equated. One native event can dirty both old and new property tuples, while edge-only effects advance an operation without any property touch. For an event, resolve and retain the complete affected tuple set before modifying proof state; deduplicate tuples only within that event using the exact full identity grammar, retaining both old/new attribution in contribution custody. First touch creates dirty_generation 1 with no seal. **Identity**

- An `id` comes from `id_seq`, shared by objects and edges. A caller MUST NOT supply one. Within `object` the primary key `(id, type_id)` is unique; global uniqueness of `id` across objects and edges rests on the sequence. An id is never reused. *(ADR-002 D2; edge ids from the shared sequence are provisional, V7)*
- Catalog ids (`type_id`, `prop_id`, `rel_type_id`) are allocated as the current maximum plus 1 under the catalog lock and are never reused, including after retirement. *(Proposed)*
- Business identity is a named UMF key (`key_def`), held in `object_key`.

**Key identity.** An object's key value for key `K` is the canonical key text `k`, stored in `object_key` with `(type_id, key_num)`.

- A key with one component uses that component's canonical text. A key with several uses the compact JSON array of the components' canonical texts, in component order, for example `["a","b"]`. The arity of a key is fixed by its definition, so the two forms cannot be confused.
- Canonical text of a component by declared scalar family: a string is its text; binary is canonical base64 text; a supported timestamp is its qualified RFC 3339 text exactly as authored (two timestamps that differ only in offset are different keys); an integer is its decimal digits with an optional leading `-`, no leading zeros, and `0` for any zero; a decimal is a plain decimal with trailing fractional zeros removed, no exponent, and `0` for any zero. Numeric lexical variants with equal mathematical value collide within the same qualified key definition (`1.0` and `1.00` are one key). The declared string/binary/timestamp families compare their canonical text; no rule here authorizes stringifying other scalar, structured or unknown families. Unsupported selected key semantics refuse before effects and remain a capability gap, not silent text equality.
- Comparison uses `COLLATE "C"`, so equality is exact bytes.
- An object that lacks a key component has no `object_key` row for that key. It is not reachable by that key and the engine reports it.
- `object_key` rows are written, updated and deleted by the same operation, in the same transaction, as the object (the engine, or a host's trigger). A change to a key component changes `k`. Deleting an object deletes its key rows by the foreign key. *(ADR-002 D9; SPIKE-003)*
- A key lookup is `object_key` joined to `object` on `(object_id, type_id)`.
- A key value an object has held is written to `key_tombstone` in the same transaction as the delete, and also when a change of key component frees the old value. With `setting.key_reuse` `"forbid"` the value then stays reserved: an import skips it and a direct create is refused (CONTRACT-004). With `"allow"` the tombstone is still written and a create may reuse the value. The database cannot enforce a reservation by a constraint, so it is engine enforcement, and a delete by plain SQL without a host trigger leaves no tombstone, which the enforcement report lists. *(Proposed)*

### Native key index capacity and large-key candidate

The proposed 1 MiB canonical-key resource ceiling is not native B-tree qualification. PostgreSQL 17 [B-tree documentation](https://www.postgresql.org/docs/17/btree.html) limits an entry to approximately one third of a page after applicable compression. The captured `object_key`/`key_tombstone` primary keys include full `k`; they cannot support every carrier below the codec ceiling merely because text storage accepts it. Qualification must pin server/block size, complete index tuple/opclass/collation and incompressible boundary cases. Compression of favorable fixtures cannot prove a universal limit.

To preserve the large-key scope, propose a separate native bucket profile rather than declaring all large legal keys supported by the old primary key. Retain full canonical `k` and its source/definition/encoding context outside any full-value B-tree entry. Index a fixed-size routing digest under the qualified type/key namespace **nonuniquely**; retain stable row identity plus the object/type/key uniqueness rule. All participating creators/re-keys/reservation writers acquire the same transaction-scoped namespace/digest bucket lock at CONTRACT-009's business-identity level, then compare complete canonical key bytes in that bucket before applying effects. Equal full keys conflict/reserve according to policy; differing full keys with equal digest coexist. Digest equality is routing/serialization only, never record identity or a unique constraint on the digest. Preserve complete bytes through retained reservation/feed/history payloads.

Native database enforcement requires unavoidable guarded derivation, bucket locking and exact-byte comparison on every advertised writer path, including direct SQL where claimed. A caller-supplied digest cannot omit the actual bucket check. The installed native digest function/dependency, typed namespace encoding, byte equality, row identity, privilege/trigger procedure and overflow limits are exact selected-profile inventory. Under an engine-only realization, classify uniqueness/derivation honestly as engine enforcement; the old full-value primary key cannot secretly remain the large-key guarantee. Bounded collision-bucket scans refuse unavailable/resource before effects if exhausted, never infer absence from a truncated scan. Read lookup uses the same digest/full-byte predicate and cannot return a different colliding key.

Migration to this candidate retains historical encoding context, verifies complete current/reserved-key collision inventory and native guards, and changes the physical profile explicitly. Retention/delete/re-key must use the same bucket protocol; no digest-based reservation purge or old-row identity reuse. Independent tests force distinct full keys into one test-profile bucket, exercise simultaneous equal/distinct creators and retained reservations, and use large incompressible carriers. Forced digest fixtures are a separate test procedure, not a production hash replacement. Exact DDL/digest/native guard and migration/rollback remain D-05 design deliverables; this proposal does not qualify existing storage or narrow the requested exact-key scope to favorable short examples.

Bucket exclusion alone cannot establish current uniqueness under an old MVCC snapshot. Add a fixed-size native bucket-guard identity `(qualified namespace,digest)` with native uniqueness and a monotonic generation updated by every participating bucket membership/reservation mutation. A writer acquires/binds the guard before full-key observation at the business-lock level. The qualified procedure must prove that its full-key observation includes prior committed bucket changes, or refuse whole-transaction retry before effects. In read-committed scopes, reobserve/revalidate after exclusion under a fresh statement observation; in a fixed snapshot, changed/newly created invisible guard state cannot be treated as an empty bucket. Use the selected native write-conflict/generation procedure to force retry rather than attempt a snapshot refresh or hidden host commit. Generation is database-derived and rolls back with effects; advisory-lock ownership or caller generation text alone is not proof.

Creation of a previously absent guard is itself serialized by its fixed-size native unique identity. A competing creator whose old snapshot cannot establish the committed guard/key contents must retry; `ON CONFLICT` or an empty SELECT is not by itself an admitted fresh observation. Guard deletion/reset is administrative and cannot race participating transactions or discard required historical/reservation context; generation cannot wrap/reuse within its epoch. All engine/native-trigger paths must use the same exact guard protocol. A row trigger discovering an unplanned earlier-level bucket lock after canonical row locks cannot silently acquire out of order: refuse/restart or require a qualified writer procedure that plans before effects. This makes raw-SQL writer coverage a concrete profile decision, not an automatic consequence of adding a trigger.

#### Candidate bucket identity and generation profile

Select proposed bucket procedure `truss-key-bucket/0.1.0`. Namespace bytes are CONTRACT-009 canonical compact JSON/UTF-8 of the ordered string array `["truss-key-bucket/0.1.0",sourceEpoch,installationId,typeId,keyNumber,keyEncodingProfile.identity,keyEncodingProfile.version,keyEncodingProfile.sha256]`. All identities/pins come from admitted native installation/catalog context; caller text cannot retarget them. Preserve exact namespace bytes with full key membership/reservation context. Numeric fields use canonical positive decimal text. This namespace is routing context, not an invented authored UMF key ID.

Compute namespace digest and full canonical-key digest as SHA-256 of the respective exact byte strings; the latter uses UTF-8 of complete canonical `k`, including its selected transport prefix. PostgreSQL 17 [binary string functions](https://www.postgresql.org/docs/17/functions-binarystring.html) supplies built-in `sha256(bytea)`. The candidate uses the qualified built-in function identity/settings, not an implicit pgcrypto installation. Other server profiles must establish the same exact function/domain evidence. Guard native unique identity is the pair of 32-byte digests, with length checks; key/reservation bucket indexes on that pair are nonunique and cannot INCLUDE the unbounded full key.

If different exact namespaces collide in namespace digest, they share exclusion/generation conservatively but remain distinct semantic contexts. Full namespace **and** full key byte equality is required after bucket routing; same digest pair cannot equate either. A test-only digest provider can force both namespace and key collisions to verify this behavior, but cannot replace the installed production function under a qualified profile. Exact-byte guards compare admitted byte carriers rather than ambient text collation.

Guard generation is native nonnegative bigint, initialized at zero and incremented with every actual membership/reservation mutation in its transaction. At `9223372036854775807`, further mutation refuses before effects; no wrap/reset/reuse is allowed in the same installed epoch. Lookup may remain independently available when mutation capacity is exhausted. Internal key-row bookkeeping uses a separately named positive bigint sequence with nonreuse/exhaustion rules and retains existing object/type/key uniqueness; it cannot consume or masquerade as a public graph identity. Proposed per-operation collision scan ceilings are 10,000 rows and 16 MiB cumulative full namespace/key bytes, counting hidden integrity rows too. Exhaustion refuses before effects/result completeness, never truncates a uniqueness decision; final resource/profile review remains required. Native generation/MVCC/lock/error/guard procedure and migration qualification remain separate from specifying these candidate identities.

### Proposed atomic key-profile migration protocol

Select the design candidate `truss-key-profile-migration/0.1.0` for an explicit administrative transition, separate from ordinary key-changing mutations and optional physical optimization. It changes selected physical/encoding bindings only through one qualified transactional installation procedure. It does not claim online migration, accept nontransactional DDL, or allow an ordinary catalog acceptance to silently toggle storage profiles. The source and target include exact layout, catalog/archive, encoding, bucket, installed-policy and resource pins, plus source epoch/installation identity. A source observation or target declaration supplied by a caller is not native installation authority.

**Preflight and exclusion.** Capture the complete original request under an original attempt identity before native effects. Validate source/target support, administrative authority, recovery custody and bounded inventory capability. Acquire the exclusive catalog/configuration head admission before any business/key/record locks, then the qualified migration exclusion. Every advertised participating writer, catalog acceptance, reservation purge and relevant retention/administrative transition must honor that exclusion. Drain/admit outstanding operations through the native profile; a flag alone cannot fence an already executing writer. If ordinary writers can bypass it, refuse activation or classify that installation as unable to supply the requested database guarantee. Current-profile reads remain valid only under their independently qualified context; a new profile must not reinterpret held historical snapshots or retained cursors.

**Independent inventory and representability.** Under the admitted coherent observation enumerate every live key membership, retained reservation and key-binding lineage required by the source profile. Include omitted/sparse memberships as classified absence, not invented keys. The inventory records complete source bytes, declaring/owner context, record/reservation identity, selected source profile and actual historical definition pins. Live records derive target bytes from admitted exact values with the target's qualified owner encoder. Deleted reservations may derive target bytes only from preserved, admitted original components or a qualified exact source-to-target conversion. An irreversible old key string, a checksum, or today's definition cannot reconstruct absent components. If any protected reservation lacks representable target identity, refuse with that complete inventory unchanged; do not discard the reservation, reactivate its object or claim an empty target bucket. Preserve original historical bytes even when a target lookup projection is available.

**Collision assessment.** Compute the complete target full namespace/key identity and routing digests for every participating live/reserved item. Compare full bytes across all target identities; digest collisions alone remain legal. Apply the admitted target reservation policy to each exact-equality class. Return every member of each forbidden class, including conflicts created by conversion and conflicts between live and deleted identities. A report that exceeds its disclosure/resource budget returns an incomplete/unavailable assessment and blocks activation; it cannot certify collision freedom from a prefix. Detailed assessment is administrative material authorized across the entire inspected owner union, not a public lookup disclosure. Resource exhaustion, missing source context, unknown identity conversion and a collision leave the old selected binding and all old rows unchanged.

**Transactional staging and switch.** Retain complete converted target candidates privately under the original owned migration transaction and exact admitted inventory. For the same-store candidate below, the live bucket's unique object/type/key tuple requires exact source revalidation and atomic membership replacement before observing pending native target parity; old/new rows cannot coexist for one membership. A shadow-store deployment requires a separately admitted layout/activation profile. Verify complete live/reserved/omitted correspondence, target full-byte equality, scope and actual installed policy before switching. Preserve graph IDs, original source facts, reservation identities, record versions and historical envelope interpretations; internal key-row IDs are fresh storage bookkeeping with retained old/new correspondence. Initialize only genuinely absent serialized guards at zero; existing source/target/colliding guards retain generation and charge every actual deletion/insertion after all-guard capacity preflight. Perform the selected-binding/configuration generation switch and durable original-attempt receipt atomically with complete installation/archive/transition finalization. Resume admitted writers only against that committed binding. CONTRACT-006's migration-aware feed v0.2 candidate supplies authored transition semantics/wires; exact native membership, producer/clock, canonical and shared binding adoption remain prerequisites for executable delivery. Never reinterpret v0.1 or emit fabricated object updates to simulate a profile change.

**Rollback and uncertain completion.** A confirmed precommit rollback restores the old binding, key/reservation membership, native policy and installation inventory; consumed internal sequence gaps are not graph mutations. Failure whose termination or transaction outcome cannot be established returns original-attempt recovery required and prevents replacement migration. Reconcile against the original immutable request, native transaction observation, exact selected binding, target inventory and original committed receipt; another migration's equal target hash is not success evidence for this attempt. Lost commit acknowledgment is not permission to rerun conversion. After confirmed commit, returning to the source profile is a new fully inventoried migration, including every subsequent live/reserved identity. It must refuse if intervening values exceed the old index/encoding capacity or lack exact reverse representation. Retained source tables are neither rollback authority nor a license to overwrite intervening writes. Removal of old physical stores/guards requires separate complete retained-reference and active-context exclusion; commit does not immediately authorize cleanup.

This resolves the proposed migration ordering, complete reservation representability and rollback semantics. Exact native exclusion/DDL/procedure, complete receipt/transition production and profile adoption, bounded collector realization and compatibility remain named design deliverables. Neither this protocol nor later test plans establish an accepted ADR, a runnable migration or native support.

**Values**

- `props` is keyed by `prop_id` rendered as text. A missing key means absent; JSON `null` means an explicit null. Meaning always comes from the catalog, never from the JSON type. *(ADR-002 D3)*
- Data matching no definition goes in `retained`, keyed by the author's field name as received, is reported, and is never dropped. *(ADR-002 D3; key format Proposed)*
- Canonical encodings: integers and decimals are JSON numbers in the author's lexical form; binary is base64 text; timestamps are RFC 3339 text with the author's offset; U+0000 is rejected with a reported rule. *(ADR-002 D3)*
- A reader MUST read JSONB, `numeric`, `bigint` and temporal values as text and parse them exactly. *(ADR-001 D3; ADR-002 D3)*
- A write renders an explicit null as `'null'::jsonb`. *(ADR-002 D3)*
- Records without identity are stored as structured values inside the owner's `props`, typed through the catalog; records with identity are objects, and composition with them is an edge with owned lifecycle, carrying `root_id` and `root_type`. *(ADR-002 D5, provisional on V3)*

**Indexes**

- Indexes other than those in `storage-layout.sql` exist only where the binding declares them; the engine never creates them in response to queries. A declared index on `object` is a partial expression index on one type. *(ADR-002 D11)*
- Planning cost grows with the number of indexes on `object`. Measured on PostgreSQL 16.2 and 17.9 with one partial index per type: planning a key lookup took about 0.1 ms with 111 indexes and about 90 to 105 ms with 1011, while a layout with no per-type indexes planned in 0.02 ms at every size (SPIKE-003). The deployment sets a budget for declared indexes per table; the default is 100, and the report lists the count. *(Proposed; default from SPIKE-003)*
- A declared index MUST be built with `CREATE INDEX CONCURRENTLY`, outside the acceptance transaction. The implementation MUST then check that the index is valid and drop and report it if not; the acceptance report lists indexes still pending. *(Proposed)*
- `edge` carries two traversal indexes: `(source_id, rel_type_id, target_id) INCLUDE (target_type)`, which is unique, and `(target_id, rel_type_id) INCLUDE (source_id, source_type)`. The unique index makes an edge unique by relationship, source and target: a second kind of link between the same two objects is a second relationship, and a repeated link of one kind needs an association object. A traversal from a source uses the index by its first two columns, and no table or index is added for the rule. *(ADR-002 D6; SPIKE-003 F9; the `target_type` include is provisional)*
- A maximum multiplicity of one is enforced by `edge_limit`, whose primary key `(rel_type_id, side, endpoint_id)` refuses a second edge: side `s` holds one row per edge of a relationship that allows one edge per source, side `t` one per target. The engine writes the row in the same transaction as the edge; the row goes with the edge by the foreign key. A maximum above one is enforced by the engine under the parent lock. No index is created per relationship, because that costs a table-wide index per relationship: at 1,000 relationships, 1,003 edge indexes made planning take about 110 ms and inserts 5 times slower, while `edge_limit` kept both at the baseline. *(ADR-002 D9; SPIKE-003 E1b)*

**Concurrency**

- **Catalog lock.** Every write transaction MUST read the current revision as its first statement, `SELECT rev FROM schema_head WHERE id = 1 FOR SHARE`, compare it with the revision it validated against, and fail as `catalog_changed` if they differ. A catalog acceptance updates `schema_head` in place, which waits for the writers holding the share lock and blocks new ones while it holds the row. Because the row is updated in place, a waiting writer locks the current version and sees the new revision. Under REPEATABLE READ or SERIALIZABLE a writer whose snapshot predates the acceptance gets `serialization_failure` instead, which is `retry`. *(ADR-002 D10; SPIKE-003: an in-place head row detected the stale writer under READ COMMITTED and failed it with a serialization failure under REPEATABLE READ; a new head row per revision accepted the stale write under both, and advisory locks accepted it under REPEATABLE READ)*
- An acceptance waits for the current writers' share locks. Under sixteen continuous writers it waited 0.5 s at the median and over 5 s at the worst (SPIKE-003), because new writers can join the lock while it waits. An acceptance therefore sets a `lock_timeout` and retries later; acceptances are rare.
- A deployment MAY add an advisory queue in front of the head row (ADR-002 D10): writers take `pg_advisory_xact_lock_shared(hashtextextended('truss.catalog', 0))` first, an acceptance takes the exclusive form first. It never replaces the head-row lock, which alone gives correct behavior under REPEATABLE READ. *(SPIKE-003)*
- A write to an object locks it `FOR NO KEY UPDATE`; a delete locks it `FOR UPDATE`, so the lock does not escalate. Composed children are locked after their parent, then in ascending `(type_id, id)` order. *(ADR-002 D9; delete lock Proposed)*
- `ver` starts at 1 and increases by 1 on every change. A writer MAY pass an expected `ver` and MUST then refuse to write if it differs. *(Proposed)*
- Cross-row rules lock the parent or run SERIALIZABLE; a deferred trigger alone under READ COMMITTED is never reported as database enforcement. *(ADR-002 D9)*
- An adapter SHOULD use prepared statements or an equivalent plan cache and MUST work without them; it reports whether it is prepared. Unprepared point reads cost about 0.01 to 0.03 ms more at 1,000 types. *(ADR-002 D11; SPIKE-003 E3)*

**Deletion.** An object is deleted by deleting its row once it has no edges; its key rows go with it by the foreign key, and the journal keeps its history. Composition and owned lifecycle are enforced by the engine, which deletes edges and owned objects first. *(ADR-002 D5, D7)*

**Enforcement layers**

| Layer | Enforces |
|-------|----------|
| Database | Typed endpoint foreign keys; no object deleted while it has edges; uniqueness of key rows per `(type, key, value)` and removal of an object's key rows with it; uniqueness of maximum-one marker rows in `edge_limit` (canonical-edge maximum-one requires qualified unavoidable marker correspondence); the JSON-object checks |
| Engine | Every assertion in the UMF model, validated before the write, naming the rule; that each object's key rows match its `props`; minimum multiplicity and aggregate invariants under the locks above |
| None | Assertions UMF carries that no layer can enforce; each is listed in the report |

The database cannot check that `object_key.k` matches the object's key components, because that needs the catalog and the canonicalization above. A write by plain SQL that bypasses the engine or a host trigger can leave the two inconsistent, and the report says so.

**Roles and extension rules for a host**

A host that builds on these tables names four roles. The roles are a convention; truss creates none.

| Role | Holds |
|------|-------|
| Owner | Owns every truss object. SHOULD be `NOLOGIN`. Creates the declared indexes. The application's login identity MUST NOT be the owner. |
| Acceptance | May run catalog acceptance (CONTRACT-003) by assuming the owner's rights through an owner-owned function. |
| Writer | Writes objects and edges, through the engine or host write functions. |
| Reader | Reads. |

- A host MAY add its own tables, functions, roles and privileges in its own schema; MAY `ENABLE` and `FORCE ROW LEVEL SECURITY` and add policies on any truss table, including the catalog tables and the journal, which can decide from the `module` that `type_def` and `rel_def` record (CONTRACT-005 is one such set, shipped as `module-isolation.sql`); and MAY add triggers on truss tables, including triggers that write the journal (CONTRACT-002) and keep `object_key` current. `FORCE` is needed because the owner and `SECURITY DEFINER` functions it owns bypass row-level security otherwise.
- A host MUST NOT add, drop or alter columns, change a primary key, foreign key or check constraint, or write the catalog tables except through a catalog revision.
- Foreign-key and unique checks run regardless of row-level security, so a key conflict or an object that still has edges can reveal that a hidden row exists. A host that must hide this decides how to report it.
- Keys in `origin` that begin `x-` are reserved for hosts.
- A host MUST declare the layout version it was built against and MUST refuse a database of a different major version.

## Precedence and Compatibility

- Precedence: ADR-002 governs. Where ADR-002 is silent, the DDL governs this document, and this document governs the other contracts. A point that ADR-002 marks provisional may change this contract by a layout version change.
- Versioning: the layout version is `major.minor`. Adding a nullable column or an index is minor. Removing or retyping a column, changing a key or constraint, or changing an encoding is major.
- Backward compatibility: a reader built for 0.x MUST ignore columns it does not know. A writer MUST refuse a different major version.
- Deprecation: an element is deprecated for one minor version before removal.

## Error Semantics

Errors are classified by SQLSTATE and the relation concerned, never by constraint name.

| Condition | SQLSTATE | Meaning to the engine |
|-----------|----------|------------------------|
| A second edge with the same relationship, source and target | `unique_violation` on `edge` | `edge_exists` |
| Edge to a disallowed endpoint type or a missing object | `foreign_key_violation` on `edge` | `endpoint_violation` |
| Delete of an object that has an edge | `foreign_key_violation` on `object` | `has_edges` |
| Key value already held by another object of the type | `unique_violation` on `object_key` | `key_conflict` |
| Key row for a missing object or an undefined key | `foreign_key_violation` on `object_key` | Engine defect |
| `props`, `origin` or `retained` not an object; `root_id` without `root_type` | `check_violation` | Engine defect |
| SQL NULL assigned to `props` | `not_null_violation` | Engine defect |
| No journal partition covers `at` | `check_violation` | Deployment must create partitions (CONTRACT-002) |
| Deadlock, a serialization failure, or a lock timeout on acceptance | `deadlock_detected`, `serialization_failure`, `lock_not_available` | `retry`: repeat the whole operation |
| Statement cannot be prepared | adapter runs unprepared and reports it | None required |

## Examples

```sql
-- a write: read the head first, under the share lock
SELECT rev FROM truss.schema_head WHERE id = 1 FOR SHARE;       -- must equal the revision validated against
INSERT INTO truss.object (type_id, props, rev) VALUES (1, '{"10":"lease"}', 1) RETURNING id;
INSERT INTO truss.object_key VALUES (1, 1, 'lease', 42);        -- type, key_num, canonical key text, object id

-- a key lookup
SELECT o.id, o.props::text
FROM truss.object_key k JOIN truss.object o ON o.id = k.object_id AND o.type_id = k.type_id
WHERE k.type_id = 1 AND k.key_num = 1 AND k.k = 'lease';

-- keyset listing of one type
SELECT id, props::text FROM truss.object WHERE type_id = 1 AND id > 100 ORDER BY id LIMIT 50;
```

## Non-Normative Notes

SPIKE-003 compared four layouts at 10, 100 and 1000 types on PostgreSQL 16.2 and 17.9 (200,000 objects, 400,000 edges): one table with a partial unique index per type, one partition per type, one table with a generic key table (this layout), and hot-type partitions plus a default partition. At 1000 types the first planned a key lookup in about 100 ms, the partitioned layouts planned a one-hop traversal in 88 to 330 ms, and this layout planned every shape in 0.02 to 0.04 ms with a fresh-connection first query of about 2 ms. It costs about 57 MB more disk (70%) than the partitioned layouts, because each key is stored twice. Not measured: declared secondary indexes on non-key properties (they remain partial indexes per type, subject to the budget above), filters on JSONB values and planner statistics (layout review concern 11), data larger than memory, and concurrent write throughput beyond the catalog-lock test. The measurements were taken on a shared laptop with other load; the differences cited are two orders of magnitude, well outside that noise.
