# `inspectBinding` Rust differential controls

This is a supplemental, separately frozen control set for the opt-in Rust
inspector. It does not modify the approved predecessor capture at
`../frozen-inspections.json`. `frozen-controls.json` records the full TypeScript
`Validation` objects generated by `tests/rust-migration/r5-binding-inspect-controls-capture.ts`;
the adjacent test checks those controls against the live predecessor and hashes
the complete prior Gate0 manifest plus the supplemental capture and output.
The supplemental suite passes on Bun 1.4.3: **5 tests, 102 assertions**.

The added cases cover missing package shape, non-document binding scope,
duplicate element/field assignments, duplicate index names and ordered index
targets, column/path schema conflict, embedded/column semantic conflict, exact
DDD field lookup, and stable relationship-ID lookup. Stable relationship
controls are produced by the existing explicit name-to-ID migration. A
renamed logical relationship remains valid under the stable ID; a missing ID
returns `BINDING_REFERENCE` after the retained unknown warnings. The malformed
column/path schema case produces two `EXTENSION_STRUCTURE` diagnostics at the
same path, matching the predecessor's complete validation output.

## Rust API boundary

The opt-in entry point is
`umf_core::binding_inspection::inspect_binding(resources, binding, logical,
ctx) -> Result<Validation, EngineError>`, with its versioned profile and exact
unsupported-version report in `rust-profile.json`. It admits only binding
vocabulary 0.1.0 and 0.2.0. For 0.3.0 it returns that explicit
`BINDING_PROFILE` Validation; it must not fall through to 0.1/0.2 validation or
claim bit128 carrier inspection.

`BindingInspectionResources` prepares the core Engine and immutable
Registry registrations for the two binding package schemas once. Each call
uses a fresh mutable Context and binding-semantic callback. Resource structs
may be shared across calls because callbacks and operation state are not stored
inside them. Cold preparation cost is paid once per resource value; warm calls
still meter parsing, structural/constraint checks, semantic scans and
validation-output work. No lock may remain held across Engine validation or a
capability callback. Inputs must remain unchanged.

The callback must match the predecessor's ordered `bindingSemantics` pass:

1. document scope and empty binding modules;
2. top-level and nested unknown warnings, followed by duplicate checks and
   field-storage checks in source-array order;
3. each index's unknown warnings, kind/predicate/expression checks, ordered
   targets and owner/path checks, duplicate table-scoped names, then includes;
4. when base validation is invalid, return its exact diagnostics without
   logical pairing or reference diagnostics;
5. only after valid base admission, check payload version/profile, core-valid
   logical source, exact paired ID/version, all element references, all Field
   or exact DDD owner/field references, then profile-specific relationship
   references.

The approved Gate0 crossed case fixes one callback-order control: an unknown
index refinement is reported before the invalid unique-kind error. Since that
error makes base validation invalid, later model-pair diagnostics are absent.
An unknown warning alone keeps `valid:true, complete:false` and still proceeds
to paired-model checks. The bad package version case returns `UNKNOWN_EXTENSION`
and `BINDING_PROFILE` before pair checking. Rust must preserve these distinct
predecessor paths and set `valid` from error severity and `complete` from an
empty diagnostic list.

Rust may use a separate reusable resource object rather than refactoring the
already frozen binding-index projection. No default routing changes are in
scope: typed access uses `complete`, several projection callers reject
`BINDING_UNKNOWN`, and other consumers accept based on `valid`. Those policies
need separate reviewed work before any caller switch. The frozen controls
define predecessor behavior; the implementation status and tested subset are
recorded below.

Hashes are recorded in `source-hashes.json`. The older inspector Gate0 report
and source manifest are pinned inputs; the extra capture and control reports
are additive. Neither manifest hashes its own README or the live test harness.

## Opt-in Rust implementation status

`umf_core::binding_inspection::inspect_binding` is implemented as an opt-in
API for the compiled-in current binding package resources. It accepts binding
vocabulary 0.1.0 and 0.2.0; 0.3.0 returns the exact refusal in
`rust-profile.json`. `BindingInspectionResources` prepares immutable core and
package validators for reuse, while every call receives a fresh `Context` and
semantic callback. No existing Delta, Iceberg, typed-access, or other consumer
is rerouted.

On Rust toolchain 1.90.0, the focused integration target
`cargo test --offline -p umf-core --test r5_binding_inspection` passes **4
tests**. It compares complete validations for all five captured 0.1 fixtures,
the 0.2 profile, Gate0 unknown/precedence/model/reference cases, explicit 0.3
refusal, and all supplemental schema/scope/duplicate/storage/DDD/stable-ID
controls. It also checks caller-input immutability and recovery after a
schema-invalid result using the same prepared resources. The frozen inputs are
the TypeScript predecessor snapshots above; this test does not widen the
supported version claim or qualify target-native behavior. Core schemas and
binding package resources are embedded from the repository source at compile
time, so this implementation claim applies to that source revision and the
bounded frozen profile only.

The six focused follow-up controls are an additive snapshot in
`review-controls.json`; the approved Gate0 `frozen-inspections.json` and
`frozen-controls.json` are unchanged. They cover both-input admission ordering,
ECMAScript numeric-key ordering during recursive admission, the exact paired
column-schema diagnostics, last-assignment lookup for index targets and
includes, and numeric-key ordering for retained unknown warnings. The Rust
admission copier is private to this API, recursively metered, and does not alter
the shared core copier. Trusted control failures whose code is `NUMBER` remain
`Err` values with control provenance. `review-source-hashes.json` is a separate
current-source receipt for these six controls, their TS capture/test, Rust
implementation/test, fixtures, relevant schemas, historical controls, and
runtime pins. The old `source-hashes.json` remains unchanged. Its historical
`package.json` digest differs from the current repository file because of
concurrent package work; the package manager remains Bun 1.4.2. The successor
receipt records the current package digest and does not redefine that older
cohort.

The six-case TypeScript predecessor check passes on Bun 1.4.3 with **1 test
and 6 assertions**; `bun run typecheck` passes. The focused Rust target passes
**4 tests**, including complete differential reports for the six cases and
control-failure provenance checks for `NUMBER` and `DENIED`. The older
historical supplemental capture remains at **5 tests, 102 assertions**.
