# R5 kind/nullability staged host-input route: opt-in, default selection held

The six kind/nullability operations remain TypeScript-selected in the Node and
browser roots. A new opt-in `umf.host-json/1` route lets Rust stage admission
for all six operations. Focused Bun/Node and real Chromium parity pass for the
frozen semantic envelopes and host-order negative controls. The implementation
is not selected as a default route: retained factory setup is expensive and
measured operation latency remains materially above the predecessor.

The focused negative-control replay is
[`negative-controls.json`](negative-controls.json), generated by
[`negative-controls.mjs`](../../../../../../scripts/rust-migration/r5/kind-nullability-default-route/negative-controls.mjs).
It executes both TypeScript predecessors and a reduced `toWire` admission
harness. The reported tagged-host paths (`/source`, `/kind`, `/nullability`,
and `/current`) are harness paths; this capture does not execute the installed
Node wrapper or establish its exact request paths. Four controls reproduce
host error-class changes in that reduced harness:

| Control | Retained predecessor | Tagged host admission |
| --- | --- | --- |
| Kind inspection with accessor in source | `UmfError`, `NON_JSON`, `/poison` | `AdmissionError`, `ACCESSOR_PROPERTY`, `/source` |
| Nullability inspection with accessor in source | `UmfError`, `NON_JSON`, `/poison` | `AdmissionError`, `ACCESSOR_PROPERTY`, `/source` |
| Kind declaration with accessor-valued invalid request | `UmfError`, `CORE_KIND_VALUE`, ideal kind path | `AdmissionError`, `ACCESSOR_PROPERTY`, `/kind` |
| Nullability declaration with accessor-valued invalid request | `UmfError`, `CORE_NULLABILITY_VALUE`, ideal nullability path | `AdmissionError`, `ACCESSOR_PROPERTY`, `/nullability` |

Two more controls show identity access order. The public TypeScript predecessor
copies source before identity and rejects the source accessor without reading
identity. The current Rust model wrapper takes module and element as positional
strings, so a binder must read `identity.module` and `identity.element` before
calling it. Both identity getters run before the wire rejects the source.
This is observable host behavior and cannot be repaired by an error-name
translation after the call.

The two verifiers are also held. Their predecessors copy and schema-check the
receipt, recompute its declaration, and only then copy `current`. The available
`verifyCoreKindDeclaration(receipt, current)` and
`verifyCoreNullabilityDeclaration(receipt, current)` wrappers send both values
through one eager tagged request. With a malformed receipt and accessor-valued
`current`, the predecessor returns `CORE_KIND_RECEIPT` or
`CORE_NULLABILITY_RECEIPT`; tagged host admission fails on `/current` before
Rust can classify the receipt. The last two negative controls retain this
counterexample.

The new host operation takes opaque input handles and orders admission in Rust:

| Operation | Rust-owned admission sequence |
| --- | --- |
| Inspect | Copy source, copy and check identity, validate source, inspect |
| Declare | Copy source, copy and check identity, validate source, check version and (for nullability) role, classify the scalar request, declare |
| Verify | Copy receipt, validate/recompute receipt, copy current, compare freshness |

Factory setup snapshots the five resource members once, creates a retained
immutable Rust `Engine`, and accounts JS snapshot/encoding plus Rust tagged
decode/catalog admission in a factory-scoped `Context` controlled by
`resourceControls` (which defaults to the factory `controls`). Resource values
are moved out of the decoded envelope before `Engine::new`, avoiding an
uncharged clone. A zero-work setup control refuses before reflecting any
resource accessor. Each method invocation gets a separate fresh `Context` for
host copies, semantic work, and result wire encoding; its `controls` ledger
resets per call. This follows CONTRACT-080 §R2: resources are admitted and
owned at factory setup, while payload budgets are per invocation. It is not one
cumulative ledger spanning factory setup and later method calls. Host
reflection reply framing remains bounded separately by the existing 600 KiB
bridge limit. The public TypeScript
predecessors have no extension registry/callback argument; the default Rust
route uses an empty registry and no-op extension capability implementation.
Unknown source content remains preserved by the frozen Rust envelope suite;
unknown declared extension IDs are skipped by both empty registries, as the
TypeScript constraint kernel does when `registry.get` misses. Custom registered
extension callbacks are outside this API and are not qualified by this route.
The adapter retains and rethrows host callback exceptions after Rust returns.

The `r5_kind_nullability` suite covers frozen envelopes, refusal outcomes,
unpaired UTF-16 labels, and retained opaque content. The opt-in Node/Bun test
and fresh-WASM real Chromium harness report six matching outcomes, eight
precedence controls, resource snapshot isolation, callback exception identity,
and cumulative `maxWork`, cancellation, meter, and per-call reset controls.
The Node test also checks both unpaired-surrogate scalar refusals. Chromium
was run with loopback permission after the sandbox refused the ephemeral local
listener. Durable outputs and exact source/runtime artifact hashes are in
[`cumulative-ledger-receipt.json`](cumulative-ledger-receipt.json). The receipt
states which artifacts were loaded directly from the workspace/package and
which fresh WASM artifacts were served from `/private/tmp`.
The diagnostic three-operation cost sample in
[`resource-cost-benchmark.json`](resource-cost-benchmark.json) measures about
27.2 milliseconds per Rust call against 1.73 milliseconds per TypeScript call
in the latest three-call run; retained factory setup took about 3.17 seconds.
Operation-schema compilation now produces immutable schemas owned by each
retained runtime, with every factory charging its own setup Context. A focused
two-factory control verifies equal setup work and refusal after an earlier
factory has been constructed. This local sample is diagnostic rather than a
release benchmark. Operation latency remains about 15.7 times the predecessor
in this fixture, so the route stays opt-in pending review and performance work.
The [operation profile and bounded optimization proposal](performance-profile.json)
pin a native sample showing recursive constraint evaluation as the dominant
call stage; production changes remain held for review.

The reduced tagged `toWire` replay above remains a harness-level capture and
does not describe exact installed-wrapper request paths. The production
host-input parity harnesses are the Node/Chromium evidence for the staged
operation interface. The scalar request path classifies strings without
traversing invalid objects; a UTF-16 string that cannot convert to Rust UTF-8
is treated as an invalid scalar. Focused Node controls confirm exact
`CORE_KIND_VALUE` and `CORE_NULLABILITY_VALUE` refusal parity for unpaired
surrogate requests.

Reproduce the focused negative controls with:

```sh
bun scripts/rust-migration/r5/kind-nullability-default-route/host-json-parity.mjs
bun scripts/rust-migration/r5/kind-nullability-default-route/host-json-browser.mjs
git diff --check
```

The capture is source-bound to the current Node wrapper and `toWire` helper. It
does not claim installed package qualification or successful default routing.
