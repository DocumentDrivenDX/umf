## Learning risks requiring explicit checks

1. An inspected action contains no stored order. Registering/assessing it grants no authority and performs no business write. Explicit evaluation APIs require supplied state; they are not a consumer executor.
2. The actual approve fixture has empty conditions and outputs. Do not add invented constraints to an illustration of that exact fixture. A separate strengthened example must be new, validated and clearly labelled.
3. Fresh keyed no-op and retained replay differ; a no-op still has a durable terminal record, while advancing no business-change version/event. Changed-then-restored primitive effects differ from net changes.
4. During invoke, a false precondition yields a durable business rejection; preview instead returns its preview result with rejected preconditions and persists no outcome/audit/outbox; output/constraint/postcondition/evaluation failure rolls back. `indeterminate` describes client uncertainty, not proven rollback. Never recommend a new token after a lost acknowledgement.
5. Frozen write permission does not imply read access; native invariant reads belong to an independently qualified consumer boundary. Handlers cannot acquire arbitrary access from a model diagram.
6. Receipts bind store/epoch/opaque version, plus qualified content and contiguous applied prefix. Arrival order, receipt epoch rotation and missing replay token do not respectively prove visibility, safe restore recovery or permission to reexecute.
7. The approve fixture uses opaque `reference-roles/1`; native executor tests copy it and explicitly select `umf.actions.roles/1` before revision retention, membership and replay-discovery provisioning. The beginner transition must display this declaration change rather than claiming the original fixture is directly native-qualified.
8. SMT/TLC/design probes, native history refinement and actual implementation mutants prove different bounded properties. No diagram or total-test count eliminates their assumptions.
