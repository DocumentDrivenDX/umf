# TD-017: Spark source authority and native interpretation

The adapter in src/adapters/spark/index.ts retains core NativeJson and delegates envelope
validation to the versioned registry. Its interpretation hook validates known recursive
DataType container shapes, then records unknown names/properties, UDT opacity and metadata
limits. The generated schemas are produced by scripts/spark-schema.ts. Future source
forms remain in the native tree; future representation fields block native-only export.

Traversal/get/edit uses existing exact-tree pointers and copied documents. A host-number
view is used only for shape inspection; it cannot become exported source or a native
metadata value. Missing field defaults remain missing. Metadata/collation names are not
silently rewritten after edits. No Spark runtime is loaded by the browser library.

scripts/spark-umf.ts extracts exact schema-case tokens (ordinary JSON.parse would round
one metadata integer), performs UMF round trips and writes a nested decimal edit.
scripts/spark-umf-oracle.py compares fresh native Python/JVM outcomes against the recorded
baseline and verifies the edit. No UDT fixture is passed to an executing native parser.
The existing local gateway is always closed. The conformance runner includes these native
stages; scripts/spark-browser.ts separately verifies public browser behavior.

Native validation must evolve into separately described runtime/configuration reports.
Future UDT/DDL/data execution requires its own explicit host contract. The initial adapter
and authored corpus do not establish those capabilities or source-to-target equivalence.

## Field-local collation rename

`src/adapters/spark/rename.ts` traverses exact native trees to select a field, constructs
eligible string paths without descending into child structs, and atomically replaces
the copied field through the existing edit validator. Null-prototype maps protect
literal `__proto__` names. Unknown metadata stays exact; unknown collation paths block.
Empty collated names block because native parsing can discard nested annotations.
The result schema is generated alongside the extension schemas.

`scripts/spark-rename-oracle.py --generate` independently constructs 20 fixtures from
native DataTypes. `spark-rename.ts` produces 17 candidates and asserts three guards;
the native oracle confirms 34 Python/JVM outcomes against separately constructed
expected DataTypes. Browser checks exercise the same cases without host globals.

Metadata diagnostics traverse the exact NativeJson tree in metadata.ts. Integer range
checks use token length and BigInt, avoiding a lossy host-number conversion. Number()
is used only to classify nonfinite binary64 conversion; it never supplies export data.
Known struct/array/map traversal excludes UDT assumptions and field-local collation maps.
Warnings extend inspectSpark without changing preservation/import acceptance.

## Browser Spark-to-Arrow schema lowering

src/projections/spark-arrow.ts retains a copied source and lowers known shapes into the
existing Arrow logical FlatBuffer model. Metadata host values are never target authority;
unknown native properties block and ordinary metadata omissions receive source paths.
Strict mode returns no target if any issue is present. Known source defaults and target
physical conventions are explicit in reports. Result schema generation lives in
scripts/spark-arrow-schema.ts.

spark-arrow-project.ts compares every generated logical model with independently decoded
native schema messages. spark-arrow-encode.ts uses the optional pinned FlatBuffers
backend; spark-arrow-projection-oracle.py independently reads targets and checks native
recoveries. spark-arrow-browser.ts executes the public projection in Chromium against
the same matrix. No Python/JVM dependency enters the public browser implementation.

## Reverse schema lowering

src/projections/arrow-spark.ts consumes the existing logical Arrow model and applies
known FlatBuffer defaults without rewriting the retained source. Recursive guards check
field/type keys and child topology before publishing a Spark target. Native-compatible
nullability widening is intentional and reported. Variant interpretation is explicit
and more structurally constrained than native marker-only detection. The result schema
is generated by scripts/arrow-spark-schema.ts. Native JSON targets are emitted through
the Spark adapter, not through Python/JVM code in the browser.

arrow-spark-project.ts compares emitted schemas to both native recovery modes, and
arrow-spark-oracle.py reparses each in Python/JVM. The browser matrix now executes both
directions. Unknown metadata semantics, extra physical types and data execution remain
separate conformance work.
